# ProtoLink v0.8.0 proposal: a complete agent harness

Status: original design proposal, 2026-10-03. Baseline: v0.7.5.

Owned local subagents and durable default-loop approvals/input are now implemented for the v0.8.0 update. Their actual APIs and recovery boundaries are documented in [local subagents](content/subagents.md) and [durable execution](content/durable-execution.md). The broader sketches below remain design proposals.
The APIs below are design sketches unless explicitly described as existing.
This document proposes scope; it does not announce implemented or released features.

## Product direction

Make this the release promise: **Build an agent in a few lines. Give it specialists, persistent sessions, controlled execution and recoverable work through the same API.**

Keep `Agent` as the public composition surface. The harness is the execution machinery behind it, responsible for preparing context, calling the model, validating actions, authorizing and executing tools, supervising children, recording outcomes and deciding when execution should stop or wait. Developers should be able to use these capabilities without constructing another competing agent runtime.

Teach five concepts first: **Agent, Tool, Session, Run and Policy**. Introduce Task, A2A cards, transports, storage protocols, context strategies and execution backends when the application needs them. Preserve the Pydantic-only base, provider-independent inference and local-first execution.

## What already exists

The current code already contains substantial harness functionality. The release should build on it and document its boundaries accurately.

| Area | Current foundation | v0.8.0 opportunity |
| --- | --- | --- |
| Composition | `Agent(name=..., llm=..., tools=...)`, configured components, ordinary typed functions | Keep one entry point and make advanced defaults easier to configure |
| Execution | `invoke`, `call_tool`, `run_task`, `start_run`, `.sync` | Consistent contracts across normal, streaming, typed and resumed execution |
| Control | `RunContext`, `RunBudget`, live cancellation, `RunHandle` | Persist execution state and supervise an entire child tree |
| Delegation | Local groups, peers, model-selected delegation, delegated events and evidence | Owned child runs with isolated context, concurrency limits and shared accounting |
| Persistence | Conversation/state storage, task snapshots, run reports, file recovery checkpoints | First-class sessions and durable execution checkpoints |
| Safety | Capability policy, authorization before execution, previews and `ApprovalBroker` | Simple profiles, durable interruptions and explicit environment boundaries |
| Context | Context manifests, history compaction, token accounting, RAG | A configurable assembly strategy, artifact offloading and selective tool exposure |
| Output | `invoke_typed`, completion checks and bounded repair flows | Native output schemas and repairs that preserve execution evidence |
| Inspection | Typed events, reports, redaction, telemetry and regression diffs | One useful run tree and lightweight application evaluations |
| Built-ins | Web, filesystem, processes, shell, Git, documents, database, storage, email/calendar and user questions | Coherent tool collections and harness-specific delegation, planning and artifact helpers |

## Recommended v0.8.0 scope

### 1. Supervised subagents

Make specialists ordinary `Agent` instances. Add a `subagents` collection that exposes controlled delegation without requiring a registry or transport for local work. Reuse existing delegation actions, task identities, evidence and events internally.

Default behavior: the lead agent owns the response; a child receives a focused request and returns a typed result, summary or artifact references. Its conversation is independent. Sharing files or application state is a separate explicit choice; a separate conversation does not imply a separate filesystem.

The contract needs:

- Parent ownership, unique child run/session identities and a visible run tree.
- Bounded active children, total children and nesting depth; start with nesting depth one.
- One root budget with child allocations or reservations, so adding children cannot multiply the allowed work. Persist consumed usage across resume.
- Permission narrowing: child tools, resources and credentials must be within the parent's authorized grant and the child's own policy.
- Cancellation propagation, deadlines and explicit fail-fast versus collect-results behavior. Cancel and await owned asyncio work, terminate managed subprocesses where the backend supports it, and report non-cooperative or in-flight effects explicitly. Ordinary Python tools remain trusted application code; async and remote cancellation are cooperative.
- Explicit partial failures and uncertain outcomes; the parent must see evidence, not just a child claiming success.
- Matching developer control through spawn, await/wait and cancel operations on run-bound child handles. Model-facing delegation and application-facing supervision must use the same engine.

Keep conversation handoff distinct: delegation returns to the lead agent, while handoff transfers responsibility for the response. Supervised delegation is the v0.8.0 default. Open-ended team mailboxes, recursive swarms and permanent background workers can follow later.

Current official SDKs support isolated specialists and ownership boundaries; ProtoLink's opportunity is to keep that behavior provider-independent and aligned with local/A2A task contracts. [Claude SDK subagents](https://code.claude.com/docs/en/agent-sdk/subagents), [OpenAI orchestration and handoffs](https://developers.openai.com/api/docs/guides/agents/orchestration).

### 2. Durable runs, approvals and user input

Introduce a small versioned execution checkpoint and action journal. SQLite is a useful first implementation; define a small replaceable protocol rather than requiring an external workflow engine.

Persist the execution cursor, model/action continuation, active agent, context references, budget usage/reservations, child statuses, pending interruptions and tool outcomes. Bind recovery to an agent/configuration version so incompatible code or tool-schema changes produce a clear migration error.

Support suspension at a tool boundary for approval or a user question, then resume in a fresh process. Decisions must refer to a server-owned pending action and the exact validated arguments, principal and resources. Changed arguments require fresh validation and authorization. Current policy must run again before a resumed side effect executes.

Use an action lifecycle such as `prepared`, `awaiting_input`, `executing`, `succeeded`, `failed` and `uncertain`. Store completed results so continuing a run does not repeat completed calls. Use a single-owner lease or equivalent claim to prevent two workers from resuming the same run simultaneously.

Recovery semantics must be honest:

- Read-only or explicitly idempotent operations can have bounded retry rules.
- Tools receive a stable idempotency key when the external service supports it.
- A crash after an external effect but before its receipt is saved can leave an uncertain outcome. Require reconciliation or an explicit resolution for non-idempotent work such as email submission or payment.
- Process/file recovery is resource-specific; do not imply checkpointing Python execution rolls back external changes.
- Custom handlers and arbitrary callbacks are resumable only when they implement the checkpoint contract. Reject unsupported resumable configurations clearly.

Persisted conversations, inspectable reports, safe report replay and executable continuation are separate capabilities. Existing file recovery checkpoints should also remain a separate resource-recovery concept.

OpenAI documents serialization of interrupted approval state and continuation of the same run. LangGraph documents the need for idempotency because incomplete work can execute again after recovery. [OpenAI approvals](https://developers.openai.com/api/docs/guides/agents/guardrails-approvals), [LangGraph durable execution boundaries](https://docs.langchain.com/oss/python/langgraph/functional-api).

### 3. First-class sessions and explicit memory

Add a lightweight `agent.session(id)` facade binding conversation identity, history and default run controls. Calling it explicitly opts that facade into scoped in-memory conversation continuity even when the parent agent is otherwise stateless; it must not change the defaults of unrelated invocations. Configured session storage makes that continuity durable across processes. Preserve `state=["conversation"]` as the existing advanced configuration. Support history inspection, clearing and optional forking through the same state/storage machinery.

Choose an isolated session for an invocation with no session identity. Explicit sessions carry continuity. This changes the current fixed defaults (`invocation_session_id` and `ask_session_id`) when persistent conversation state is enabled, so provide a migration recipe for applications that intentionally used shared history.

Explain four kinds of persistence clearly:

| Data | Meaning | Default behavior |
| --- | --- | --- |
| Conversation | Messages for one session | Scoped by explicit session; no cross-user sharing |
| Application memory | Saved facts or records | Explicit reads/writes through storage or retrieval |
| Execution state | Cursor, pending work, receipts and usage | Written only with durable execution configured |
| Artifacts | Large outputs, documents and evidence | Referenced by ID with scoped access |

Avoid automatic long-term fact extraction as a default. Optional memory strategies need provenance, deletion and application/user namespace isolation. Session IDs are partitions, not authorization credentials; services still authenticate users and authorize access to their partitions.

### 4. Context management and artifact offloading

Give the existing manifest and compaction machinery an application-facing context strategy. It should decide what enters each model call: instructions, relevant conversation, current goal, approved resources, pending work, selected tools and retrieved evidence.

Add configurable thresholds for tool-result previews and artifact offloading. Keep full results in an artifact store and return a bounded preview plus reference; provide a scoped retrieval tool so the agent can inspect details later. Artifacts must be available to authorized children and clients, not exposed globally by a guessable ID.

Compaction must preserve required instructions, current user constraints, pending approvals, unresolved tool calls, task progress, recent turns and evidence references. Keep tool-call/result pairs valid. Summaries are derived context; retain original evidence according to the application's retention policy.

Make preparation inspectable: expose a manifest of included, omitted, compacted and offloaded context. Keep provider-specific caching and compaction optional behind declared capabilities.

This pattern is reflected in Deep Agents' documented separation of skills, memory, summarization/offloading and isolated subagents. [Deep Agents overview](https://docs.langchain.com/oss/python/deepagents/overview).

### 5. Better tools and structured results

Improve the tool execution contract rather than expanding the catalog indefinitely.

Add explicit effect/retry metadata, configurable deadlines, output bounds and typed business outcomes. Distinguish a business rejection from invalid arguments, authorization denial, timeout, provider failure and uncertain external execution.

Offer optional lazy tool catalogs for large MCP or application inventories. Small sets remain eager. Search only configured and authorized tools; validate loaded definitions and preserve deterministic names/order. Loading a tool must not bypass policy or automatically trust remote annotations. Avoid requiring embeddings or another model for basic discovery.

Extend existing `invoke_typed` with provider-native output schemas where supported and a validated JSON fallback elsewhere. By default, repair invalid final output from recorded evidence with side-effecting tools disabled. Rerunning the original workflow must be a separate explicit choice, since current `max_attempts > 1` can execute tools again.

Expose provider capabilities for native tools, structured output, parallel calls, multimodal inputs, usage and continuation. Capability negotiation must report unsupported requests instead of silently promising parity. Support multiple independent tool calls only under bounded scheduling and declared execution rules.

OpenAI's tool search loads deferred definitions on demand. MCP's current tool contract includes structured results and output schemas, but tool annotations require a trust decision. [OpenAI tool search](https://developers.openai.com/api/docs/guides/tools-tool-search), [MCP tools](https://modelcontextprotocol.io/specification/2026-07-28/server/tools).

### 6. Policies, hooks and completion criteria

Compose readable profiles for common applications: read-only research, approved workspace changes and custom capabilities. Reuse `CapabilityPolicy`, existing previews and built-in assistant defaults. Define resource scope as well as capability names: paths, origins, accounts, database permissions and credentials.

Add small typed extension points for context preparation, model selection, input/output validation and execution observation. Establish one order: prepare and validate, authorize, persist execution intent, execute, persist outcome. A crash between effect and committed outcome may be uncertain. Extensions must not replace the final policy boundary or give a child more permissions. Observation failures and enforcement failures need separate documented behavior.

Offer an ergonomic typed application-dependency context for tools and hooks: database clients, authenticated principal, tenant scope and application services are supplied by the developer, rather than global variables or model-generated arguments. Keep this context distinct from serializable `RunContext` metadata. Secrets and live client objects must not enter prompts, reports or checkpoints; durable resume resolves them again through application-owned providers.

Keep automatic guardrails, permission enforcement and human approvals distinct. A content classifier can be useful, but the concrete tool boundary still enforces authority. Label externally supplied material and child summaries as data; they cannot grant tools or permissions. Remove the fallback path's promotion of tool/child content into system messages while preserving valid provider message formats. Test instruction-like tool output with both native and JSON fallback models.

Build on `CompletionCheck` and `RepeatUntil`: callers can require a condition such as a valid schema, produced artifact or passing configured check before a run is considered successful. Bound repair and detect repeated actions without progress. Success requires the application's evidence, beyond a model's final sentence.

### 7. Run inspection and lightweight evaluations

Extend existing events, reports and devtools to show parent/child execution, suspension points, approval decisions, context changes, stop reasons and measured usage. Keep one normalized stream across local, remote and resumed paths. Add a convenient user-text view that does not leak JSON control actions; retain raw chunks for advanced users.

Bound event queues and in-memory retention, support persistent event cursors where durability is configured, and define backpressure/overflow behavior for slow consumers. Critical action receipts and interruption/status events cannot be silently dropped. A consumer leaving a stream and a caller cancelling execution remain separate operations.

Build a small evaluation helper on the existing mock model, report assertions and report diffs. Applications supply cases, scripted responses/tool overrides and ordinary evaluator functions. Measure answer validity, tool trajectory, unauthorized actions, task completion, budget usage and latency. Model-based grading is optional and explicitly incurs model usage.

Keep trace redaction separate from execution data needed for recovery: a redacted diagnostic report may not be sufficient to resume. Durable stores need scoped access, retention and an explicit secret-handling contract. Do not export private traces by default.

Extend the existing per-model token/cost metrics into run-tree accounting. Distinguish measured tokens from estimated cost. Use an application-supplied pricing resolver and reservations; do not claim an exact spend ceiling when provider usage, rates or in-flight requests cannot establish one.

Official testing/evaluation patterns support fake models, reusable cases and trajectory grading. [Pydantic AI testing](https://pydantic.dev/docs/ai/guides/testing/), [OpenAI agent evaluations](https://developers.openai.com/api/docs/guides/agent-evals).

## Valuable optional additions

**Reusable instruction skills.** Explicitly configured local skill sources can progressively load instructions and resources for tasks such as reviewing a contract or maintaining a repository. Their inclusion must not grant authority or automatically run scripts. The current `skills="auto"|"fixed"` controls A2A card metadata, so choose a separate `skill_sources` field/type instead of changing that meaning. A2A `AgentSkill` remains capability metadata.

**Task planning.** A small persistent task-list tool with statuses, dependencies and evidence links helps long runs and UIs. Planning stays optional. Bind actual completion to execution evidence rather than treating a checked box as proof.

**Execution environments.** Reuse `ExecutionBackend` and add an optional concrete container/remote adapter with documented filesystem, network, process and credential boundaries. A policy check or working-directory restriction does not provide OS isolation. Build this as an optional integration with no extra base dependency; ship it only when its isolation claims can be tested. All relevant tools must obey the configured environment boundaries.

**Tool collections.** Provide transparent collections for research and coding using existing factories. Developers must still see which tools are added, their resource scope and mutation permissions. Keep account credentials and user interaction callbacks explicit.

Skills, lazy discovery and a task list are good additions if the core runtime contracts are stable. A fully managed sandbox service, browser/voice platform, distributed scheduler, recursive agent teams and visual workflow builder should be later work or external adapters.

## API direction

Keep the existing `llm`, `system_prompt`, `tools`, `invoke`, `call_tool`, `start_run`, `run_task` and `.sync` vocabulary. Avoid adding `brain`, `model`, `execute` and `run` synonyms for concepts already served by those names.

Illustrative v0.8.0 API; `subagents` and `session()` are proposed:

```python
from protolink import Agent


def lookup(topic: str) -> str:
    """Read a topic from the application's knowledge base."""
    return knowledge_base.lookup(topic)  # Application-owned implementation.


checker = Agent(
    name="checker",
    llm="ollama:your-model",
    system_prompt="Check the evidence and return corrections.",
    tools=[lookup],
)

assistant = Agent(
    name="assistant",
    llm="ollama:your-model",
    tools=[lookup],
    subagents=[checker],
)

answer = await assistant.invoke("Explain the findings and verify them.")

session = assistant.session("user-42:conversation-7")
answer = await session.invoke("Summarize our current report.")
answer = await session.invoke("How does that compare with our earlier report?")
```

The session facade binds continuity; storage and state remain explicitly configurable. The earlier isolated `assistant.invoke()` does not automatically enter the new session. Documentation should make the ephemeral versus persistent choice visible.

Existing API for more control:

```python
from protolink import RunBudget

handle = assistant.start_run(
    "Explain the findings and verify them.",
    budget=RunBudget(max_steps=20, max_llm_calls=8, max_runtime_seconds=120),
)

async for event in handle.events():
    render(event)  # Application-owned UI callback.

result = await handle.result()
```

Proposed durable extension: `agent.resume(run_id, ...)` loads a configured server-owned checkpoint and returns the same kind of run handle. Add a typed interruption response operation with correlation and stale/duplicate-response handling; choose its final signature after the checkpoint design. `invoke` can use a configured live handler, but must expose a typed interruption when no handler can immediately resolve required input.

Use a small optional typed defaults/configuration component for child limits, context strategy and durability. Per-run options override defaults explicitly and cannot weaken configured policy. Avoid adding dozens of independent constructor flags or forcing beginners to understand all configuration types.

Keep local, streaming, typed and resumed calls on one internal engine. Treat transport/A2A compatibility as a boundary around that engine. Add conformance tests for unsupported remote operations rather than hiding the difference between a ProtoLink peer and a generic A2A service.

## Implementation order and boundaries

1. Define the session, child ownership, interruption, checkpoint and journal contracts, including migrations and serialized versions. Publish API sketches for review.
2. Implement isolated sessions and supervised local children using existing execution primitives. Add root accounting and bounded concurrency before allowing fan-out.
3. Implement SQLite checkpoints, durable approvals/questions and recovery of supported default-loop runs. Prove crash recovery and uncertain-effect handling.
4. Add context/artifact handling, native typed output and safe repair. Integrate extension points and policy profiles through the same loop.
5. Finish run-tree inspection, application eval helpers, documentation and executable examples. Add optional skills/tool discovery only once their contracts compose cleanly.

Durable default-loop execution and supervised local children are release gates. Distributed durable ownership across machines, arbitrary Python handler continuation and automatic recovery of unknown external effects are out of scope for the first release.

## Documentation, examples and changelog

Give the documentation three clear paths: a short tutorial, task-oriented recipes and the complete API reference. Preserve existing deep references but lead with minimal working code and concrete behavior.

Required guides: harness concept, sessions/memory, subagents, streaming/control, approvals and questions, restart/resume, context/artifacts, policy/environments, typed results, evaluation/testing and local-to-A2A serving. Include a provider capability matrix and an upgrade guide from 0.7.x, especially session defaults and repair semantics.

Required one-file examples:

1. A typed tool and one agent.
2. An explicit session with two turns.
3. Streaming progress and cancellation.
4. Two specialists with concurrency and a shared budget.
5. Approval, process restart and resume.
6. A large tool result retrieved through an artifact.
7. A typed result with output-only repair.
8. Completion checks and a bounded repair flow.
9. A local agent served remotely with the same task contract.
10. An evaluation case detecting an unauthorized or repeated action.

Provide deterministic provider-free variants and a documented real-provider setup. Offline examples must use genuine runtime/tool results, not fabricated success strings. Run examples and assertions in CI; verify failure paths and expected outputs as well as process exit. Reuse runnable source in docs where possible to prevent drift.

Start changelog work with an **Unreleased 0.8.0** entry during implementation. Separate new features, improvements, fixes and migration changes. Link every headline to its guide and runnable example. Document recovery limits, remote cancellation and any experimental APIs. Assign the release date and update package/docs metadata only when the release gates pass.

## Release quality criteria

Replace "perfect code" with explicit guarantees backed by tests and evidence:

- Async and sync parity, installed-wheel behavior, minimal dependency import and current supported Python/dependency matrices pass existing lint, typing, package and documentation checks.
- Framework-managed conversation, checkpoint, approval and artifact access respects server-owned principal/resource scopes under concurrency. Custom tools and stores must honor the same scopes; trusted in-process Python code is not an adversarial isolation boundary.
- Child cancellation cancels and awaits cooperative owned asyncio work and terminates supported managed subprocesses; sibling failure follows the configured policy. Non-cooperative work and in-flight effects remain explicit and all child outcomes inspectable.
- Runtime-mediated delegation cannot widen permission grants, access another tenant's managed resources or escape root work limits by delegating again. Test racing budget reservations and already in-flight work.
- Restart tests cover each checkpoint boundary, expired/duplicate approval responses, worker lease conflicts and configuration-version changes.
- Crash after an external side effect yields an uncertain outcome unless reconciliation or service idempotency proves a safe continuation. Non-idempotent calls are never blindly replayed.
- Context compaction preserves constraints, pending work and valid tool-message pairs. Large outputs remain retrievable with authorized access.
- Instruction-like tool and child content stays in observation context and cannot widen authority. Slow event consumers cannot cause unbounded memory growth or lose critical execution receipts.
- Typed output repair does not repeat original mutations by default. Repeated/no-progress work stops with a clear reason.
- Diagnostic redaction, recovery data and retention have separate tests and documented behavior.
- Local/remote/streamed event contracts, reports and stop reasons agree where the transport supports the operation.
- Record before/after infer-loop evaluations for the affected prompts, models and delegation behavior, including a small/local model and a hosted native-tool model where available. State unavailable live evaluations explicitly.
- Every tutorial runs, the docs build succeeds and changelog/version/migration links agree with what actually ships.

The resulting release is substantial because it connects the existing pieces into an operable harness: clear session ownership, supervised specialists, durable waits, controlled context, safe output repair and evidence of completion.
